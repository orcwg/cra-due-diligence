# What is due diligence

## Properties to check for due diligence

The purpose of due diligence is to ensure that the integrated open source components are in a state that they do not
compromise the cybersecurity of the product. 
This can mean that the development practices ensuring good code quality, have a way to report
vulnerabilities, react to the reported vulnerabilities and release fixes.
This chapter collects a selection of example properties what can be checked as the due diligence.
CRA introduces voluntary attestation as a way for open source communities to support the due
diligence of the projects. This voluntary attestation could provide the necessary data about the
project properties identified in this chapter to carry out due diligence.

### Project correctness

Open source projects are forked in many cases. One primary reason is the contribution workflow of
major software development platforms where the open source projects are developed (e.g.: github.com
and gitlab.com). Another reason can be that a developer or a set of developers just would like to
drive the project to a different direction or would like to experiment with the technology. When
integrating open source components the source of these components should be always the major upstream
and not an undermaintained fork.

### Development practices

Development practices of the integrated components are a critial part of due diligence. The correct
development practices elnsure that the code of the component is always peer reviewed and tested.

**Number of approvals for reviews:** The project should enforce the peer review for every change. This
means that all changes should have a review process (GitHub Pull Request, GitLab Merge Request, Gerrit
Change Set or similar) and there should be at least one approval from a person who is not the
proposer of the change. With this, it is ensured that a single person who takes over an open
source project can not inject malicious code to the products consuming the project.

**Automatic software testing:** The project should have automatic testing set up which runs for all
change request before the changes are merged. This guarantees that the quality of the software is
sustained and not vulnerabilities are introduced.

**Regular releases:** The project should have regular releases. In this way the vulnerability fixes of
the project are consumable by the products integrating the project. 

### Governance

**Sustainable governance:** The project is governed in a way that is sustainable for the foreseeable duration of the
product life-cycle and minimum support period. Examples may include having a published project succession plan, an
active core group of co-maintainers, or a registered non-profit legal entity governing the project.

### Vulnerability handling

Naturally it is a critical factor of due diligence how the projects handle vulnerabilities.

**SECURITY.md:** The project should have a `SECURITY.md` or similar file where it is described how can
users report vulnerabilities and what is the process to address the vulnerabilities.

**Vulnerability handling:** The proejct should not neglect vulnerabilities. The reported
vulnerabilities should be addressed in a timely manner.
