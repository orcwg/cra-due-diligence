# How open source projects and stewards can help manufacturers to achieve due diligence

- Voluntary attestation
- Provide security history
- Maintain security process description and evidence it is followed

## Test data for integration testing

Article 13(5) of the CRA requires a manufacturer to exercise due diligence on the components it integrates, and Recital 34 lists the actions that satisfy it: checking for the CE marking, checking the security update history, checking the vulnerability databases, or "carrying out additional security tests".
A free and open-source component that was not made available on the market in the course of a commercial activity carries no CE marking, so the security tests are a possible evidence for it.
A project cannot test an integration it has never seen.
It can ship what an integrator needs to run those tests inside the integrator's own product.

Security testing of the whole product happens at product level, after integration and due diligence, because an open source project has no information about how it is integrated to a product.
Tests published by an open source project are one input to the product level security testing and do not replace it.
Nothing in this section is a requirement on a project.
It lists what a project may ship, and a project that ships none of it leaves the integrator to write its own tests, as today.
