# How open source projects and stewards can help manufacturers to achieve due diligence

- Voluntary attestation
- Provide security history
- Maintain security process description and evidence it is followed

## Test data for integration testing

Article 13(5) of the CRA requires a manufacturer to exercise due diligence on the components it integrates, and Recital 34 lists the actions that satisfy it: checking for the CE marking, checking the security update history, checking the vulnerability databases, or "carrying out additional security tests".
A free and open-source component that was not made available on the market in the course of a commercial activity carries no CE marking, so the security tests are a possible evidence for it.
A project cannot test an integration it has never seen.
It can ship what an integrator needs to run those tests inside the integrator's own product.

Security testing of the whole product happens at product level, after integration and due diligence, because a project does not know how its component is integrated.
Tests shipped by a project are one input to that testing and do not replace it.
Nothing in this section is a requirement on a project.
It lists what a project may ship, and a project that ships none of it leaves the integrator to write its own tests, as today.

The core of it is a set of test vectors, each pairing an input with the result the component should return.
Reject cases matter most.
That is where independent implementations tend to disagree.

A manifest pins the component revision and the vector revision together, so any result traces back to both.
A runner in the integrator's build re-runs the vectors on each update and names the vector whose result changed.
When the project fixes a vulnerability, it adds a vector that reproduces it, and the integrator's next run shows whether the fix holds in their own build.

An integration guide states what the component needs from its operating environment: the security functions it relies on the product to provide, and the configurations it does not support.
Where an assumption can be tested, the project ships a test with the guide.
A library that relies on the operating system for randomness, for instance, can ship a check that fails when no secure source is available, and the integrator runs it where the component is deployed.
The project can also state the type and level of testing it performs, which the integrator can cite in the manufacturer's own assessment.

Each run's outcome belongs in the due diligence record described in chapter 3.
It is one checked property, with the test output referenced by its cryptographic digest.

Appendix A works through one example with a published vector set, agent-evidence-vectors release 0.25.0 (`agent-evidence-vectors==0.25.0` on PyPI), run against a library that verifies signed evidence records.
It shows the commands, how to read the output, and what the integrator records.
